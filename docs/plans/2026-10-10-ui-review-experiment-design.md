# UI専用独立レビュー実験 — 設計案 v0.1

状態: 実験用の設計案。2026-10-10作成。文書保存は承認済みだが、常設エージェント・コマンド・hookへの組込みは未実施。

## 1. 目的と今回の範囲

実装担当の会話・意図・自己評価を引き継がず、現在の画面と操作を、利用者の業務と明示された基準から評価する。最初の対象はHKBS入金突合の現行ローカルデモ。レビュー結果を返す実験であり、UI修正・実サービス連携・実装開始を含まない。

今回保存するのは本書、[最小ガイド](../../shared/ui-review-guide-experimental.md)、[手動実行用プロンプト](../../shared/ui-review-prompt-experimental.md)の3文書だけ。既存の `::pr-review`、`::publish`、自動hook、既存エージェント定義は変更しない。レビュー実験は親が別の新規タスクとして起動する。

## 2. 配置の判断

[CLAUDE.md](../../CLAUDE.md)は、ツールに依存しない本文を `shared/`、Claude用の入口を `claude/agents/`、Codex用の入口を `codex/skills/` に分ける。既存の `docs/plans/` も確認したため、設計案を同所に、汎用ガイドとプロンプトを `shared/` に置く。

HKBSの固有要件や採用判断の正本はHKBS側に残す。AgentSkillsへ議事録全文・顧客データ・チェックリストの複製を作らない。今回の文書は登録済みSkillや擬似コマンドではなく、読み込んで使う実験素材である。将来入口を作る際はツールごとの配置・互換配置・README更新規約を別途適用する。

## 3. 最小構成と起動契約

1. 親が下記の入力契約を埋め、基準と対象画面の版を固定する。
2. 会話履歴をforkしない新規レビュータスクへ、最小ガイド・レビュープロンプト・入力契約だけを渡す。
3. レビュー担当が指定URLの実画面と代表操作を確認し、根拠付きの報告を返す。
4. 親と利用者が修正・受容・却下を判断し、必要なら対象プロジェクトの正本を更新する。

「親の意図を使わない」という文章だけでは、起動時の会話継承を防げない。親は起動方式と継承設定を記録する。本環境の委譲ツールなら新規タスクで `fork_turns: "none"` を指定し、既存の実装タスクを再開しない。これは起動側の設定であり、共通本文には製品固有の起動構文を持たせない。

Claude Codeを使う場合は、定義を指定したnon-forkの新規サブエージェントを使い、fork型やresumeを避ける。[公式資料](https://code.claude.com/docs/en/sub-agents#what-loads-at-startup)では、non-forkは新しい文脈から始まる一方、委譲文、プロジェクト規約、起動時に指定したSkill等は入ると説明されている。委譲文自体への実装会話の混入も防ぐ。

独立したCLIプロセスを使う案は、通常端末からの新規読取専用セッションに限って別途検証する。既存 [review-staged-diff.sh](../../common/reviewers/review-staged-diff.sh) は読取専用・一時セッションで起動するが、Codexセッション内の入れ子起動を止める既存ガードもある。これをUI実験のために迂回しない。現在の [code-reviewer.md](../../claude/agents/code-reviewer.md) にはツールの読取専用制限がないため、定義をそのままUIの読取専用実行保証として扱わない。

会話を渡さなくても、システム指示・プロジェクト規約・共有ファイルは残る。永続メモリ、作者の検証報告、旧レビュー、履歴全体は入力に含めず、読取対象を限定する。完全な情報隔離を本書だけで保証はしない。実行時に実際の起動設定・許可された入力一覧・自動読込を記録し、確認できなければ隔離は「未検証」と報告する。

## 4. 入力契約

実装担当の会話要約を渡す代わりに、次の5区分の事実を渡す。実行条件・版・対象範囲はURLと基準のメタデータに含める。下表の未設定項目は親が実験前に確定する。

| 区分 | 必須の内容 |
|---|---|
| 利用者 | 役割、達成したい業務、利用言語、操作環境。能力や習熟度を推測で確定しない |
| 業務仕様 | 現在採用済みの期待結果、対象と対象外、正本のパス・ID・出典・決定状態。未決事項は未決と記す |
| URL | 実際に開くローカルURL、対象画面、レビュー時刻、source commitと対象dirtyファイルのhash、runtimeを識別するasset/bundle/image情報、画面幅。source/runtimeの対応は確認結果を分ける |
| 代表データ | 架空・匿名のfixture ID、初期状態、操作手順、期待する結果、再初期化方法。実顧客データや秘密情報を渡さない |
| 基準 | ガイド版、適用する一般基準・顧客基準・確定仕様のID、短いシナリオ、対象外、停止重大度、許可された参照・操作、現在有効な決定の最小索引 |

業務・顧客基準は `id / expectation / scope / status / source / supersedes` を持たせる。確定済みとして扱えるのは、確認できた権限者の採用根拠があるものだけ。議事録の発言・提案・作者説明を勝手に採用へ変えない。未決や競合があればその項目の判定を保留し、他の確認を続ける。

runtimeが現行sourceに対応することを確認できない場合、画面で観測した結果とsourceに関する推論を分ける。古いbundleの可能性を隠して最新版の合否を出さない。

入力から除外するもの: 実装意図、試行錯誤、作者のPASS、過去レビューの合否や修正誘導、会話全文、無関係なSESSION_BRIEF、WORKING_MEMORY、Secrets、.env、認証情報。適用規約は守るが、そこに書かれた自己評価を画面の合格根拠にしない。

## 5. 基準と履歴の分離

| 層 | 保存先・役割 | レビュー入力への渡し方 |
|---|---|---|
| 一般原則 | AgentSkillsの最小ガイド。情報階層、操作の分かりやすさ、状態・エラー、アクセシビリティの観点 | ガイド版と該当ID。規格と経験則を区別する |
| 顧客固有 | 対象プロジェクトの顧客ルール。用語、言語、役割、承認方法など | 採用済みの短い基準と出典のみ。提案・未確認は判定根拠にしない |
| 確定仕様 | 対象版の業務・画面仕様の正本 | ID参照と操作シナリオ。既存正本へ期待を重複管理しない |
| 採用・却下・受容履歴 | 対象プロジェクトの決定記録。決定者・日時・適用範囲・置換関係 | 現在有効な決定・例外の最小索引のみ。議論や過去レビュー本文は渡さない |

たとえばHKBSで縦配置が採用されても、「すべてのUIを縦に並べる」を一般原則に追加しない。現在の顧客・画面・幅で有効な採用判断として扱う。一般観点の「関連情報を理解できる」は、実際の作業阻害が再現できたときにだけ不具合の根拠にできる。

決定索引は `decision_id / rule_or_finding_id / disposition / scope / effective_version / source / supersedes / reopen_condition` を持つ。採用、却下、残存リスク受容、修正済みを区別する。レビュアー自身は採用・受容を決定しない。

受容済みの同じ指摘は、同じ適用条件では繰り返さない。修正済みの問題が再発した場合、適用範囲外で再現した場合、期限切れ、新しい影響やリスク増大が確認できた場合だけ、元IDと再提示理由を付けて報告する。採用済みのレイアウトへの単なる好みの異議は再発ではない。

## 6. レビューと報告

一般基準の実害、顧客固有の採用事項、確定仕様への違反をそれぞれ確認する。まず表示・操作を観測し、必要な範囲だけDOMや許可された現行sourceで確かめる。スクリーンショットだけで操作の合否を、DOMだけで読みやすさを断定しない。

指摘は `finding_id / category / rule_ids / source / observed / expected / reproduction / evidence / impact / severity / confidence / minimum_action` を持つ。根拠ID、再現、利用者への影響、重大度、確信度、最小修正案を必須とし、画面の識別情報と必要ならファイル・行も付ける。

不具合、未決仕様・確認不足、好みや改善案を別枠で出す。不具合の重大度はP0〜P3、確信度は高・中・低。疑いは確認事項に留める。最初のHKBS実験はP0/P1を停止条件とする案で、P2/P3や好みだけから停止を自動決定しない。判定は明示した条件・版の範囲に限り、本番受入やWCAG適合全体を認定しない。

複数視点の議論は次段階の案とする。実施するなら、業務操作の視点とアクセシビリティの視点が、それぞれ同じ最小入力から独立した初回報告を作り、その後に根拠を比較する。1人が複数視点で確認した結果を、複数人の独立レビューと呼ばない。意見の不一致や仕様変更は利用者が判断する。

## 7. 第一実験: HKBS入金突合

対象リポジトリ: `D:\Git\OtherRepositories\SAI-zeiri-HK\HKBS`。対象アプリ: `apps/payment-demo/`。READMEに記載された動的URL候補は `http://127.0.0.1:3109/payments`。本書作成時には接続・現行bundleとの対応を検証していないため、親が実際のURLとruntimeを確認してから入力する。静的mockと動的デモは混同しない。

正本の参照候補:

- 範囲: `docs/2026-10-03_契約対象業務_自動化スコープ対応図.svg`
- 構造化業務要求: `docs/business_flow_definition.yaml`
- UI期待: `docs/2026-10-08_入金突合UI_指摘と受入チェックリスト.md` の現在有効なPUI行
- 顧客発言の出典: `mtg-transcript/2026-10-02_1502_Kenji_SHIGIYA・中翔他.md` の必要な時刻だけ

チェックリストは、最新版の期待と置換済み履歴を同じファイルで管理する。作者のPASS・旧版スクリーンショットは独立確認の代わりにならない。期間の長さはYAML参照、起算日・境界・時刻/TZ等の未決事項は未決のまま扱う。READMEの古い「顧客未確認」等を優先して最新の採用事項を戻さない。

親は現在有効なPUI IDから、処理前/後の移動、単独・共通入金の候補確認、人による確認と結果表示、差額/保留、言語切替など必要な代表シナリオを選ぶ。これは入力を作るための候補一覧であり、旧フローや分割を新しい要求として復活させない。具体的なタブ名・件数・配置は実験開始時の正本から固定する。

実験では隔離したブラウザの架空データを使い、必要な画面操作と一時的なデモ状態変更だけを許可する。UI/source/設定の編集、本番データ、外部API、メール送信、会計・Xero書込、Secrets、commit/push/外部投稿は禁止。報告は返答で受け取り、チェックリストの合格印や決定記録はレビュアーが更新しない。

## 8. 軽量commitとPR詳細の運用案

将来修正を行う場合、commit本文は「何を変えたか・なぜ」の短文と必要な指摘IDだけにする。レビュー全文や議事録全文を毎commitへ埋め込まない。

PR説明には、利用者の問題と変更後の挙動、対象UI/基準版、解消した指摘ID、検証したURL・版・シナリオ、証跡リンク、未検証範囲、受容した残存事項と決定IDを残す。長い証跡は専用記録を参照する。

UIレビューは既存のコード/差分レビューと別の証拠であり、[::pr-review](../../common/prompts/pr-review.md) の代替ではない。[::publish](../../common/prompts/publish.md) の必須確認にするかは対象タスクで明示する設計案で、現状のhookやgateがUI報告を自動検査するわけではない。今回は文書を未commitで保存するだけ。

## 9. ガイド更新手順と実験の評価

1. 新しい観測と出典を記録し、一般原則・顧客固有・確定仕様・決定履歴のどこに属するか判定する。
2. 議事録の提案は提案のまま置き、権限者の採用根拠を確認したものだけを正本へ反映する。
3. 既存IDを保ち、置換関係・適用範囲・有効版を更新する。顧客の個別採用を一般原則へ昇格させない。
4. 期待が変わった項目の旧PASSを無効にし、次の新規レビュー入力を短く作り直す。
5. 汎用ガイド変更は別の明示した変更として扱い、版を上げる。reviewerがその場でガイドを書き換えない。

最初の実験では、親会話の混入、根拠のない仕様追加、好みの不具合化、受容済み指摘の反復、版違いのPASSがないかを評価する。正当な不具合を見つけたかと同時に、根拠不足を保留できたかを確認する。常設化・自動登録・複数レビュー運用は、この結果を見て決める。

## 11. 第一実験の結果と学び — 2026-10-10

訂正済み入力v0.2で、代表5シナリオの実操作と11画像の実画素確認を実施。最終判定はWARNING、確認範囲でP0/P1なし、P2はモーダル終了後のフォーカス復帰と1024幅English差額末尾のclipの2件。UIは修正していない。[最終報告の原文](../experiments/2026-10-10-hkbs-ui-review/2026-10-10_UI独立レビュー実験結果_v02_最終.md)と[操作証跡](../experiments/2026-10-10-hkbs-ui-review/2026-10-10_UI独立レビュー実験_v02_操作証跡.md)、[画像索引](../experiments/2026-10-10-hkbs-ui-review/2026-10-10_UI独立レビュー実験_v02_画像索引.md)を保存し、[報告と11画像をまとめた閲覧用HTML](../experiments/2026-10-10-hkbs-ui-review/2026-10-10_HKBS_UI独立レビュー実験_v02_最終報告.html)を作成した。原文と画像は変更せず、Libraryへのユーザー向け保存は閲覧用HTML1件に絞る。

- 入り口で最新のユーザー採用仕様、source worktree、runtime、ガイド版を一緒に固定する。元repoの古いチェックリストを公開元worktreeの基準として渡した初回入力の取り違えを訂正した。第7節の初回候補を現行期待として使わず、採用事項を限定抽出したv0.2を優先する。
- 実装者のself-reviewやPASSは初回入力に渡さない。準備担当が供給するsource hash、image、buildId等のruntime対応証明は対象版の識別に使用できるが、UIの合格証拠とは分ける。
- シェル障害時は、許可済み資料を通常のファイル読取で転記した自己完結入力、HTTP画面の実操作、別取得役の画像を使用できる。評価はレビュアー自身が行い、画像取得者・操作状態・自力未検証のhash等を明記する。拒否されたブラウザfileアクセスは再試行・迂回しない。
- 製品の重大不具合とレビュー証拠不足を別に判定する。今回のP2は非停止の製品指摘で、画像不足による実行上のBLOCKERは最終報告では解消。対象外・未検証を保ち、本番受入やWCAG全体の合格へ広げない。
- 今回は手動実験の記録まで。自動hook、既存 `::pr-review` / `::publish`、アプリソースは変更していない。
