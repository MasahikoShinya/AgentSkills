# UIレビュー最小ガイド — 実験案 v0.1

状態: 2026-10-10作成の手動レビュー用実験案。自動適用・製品の正式受入基準・アクセシビリティ適合宣言ではない。

[設計案](../docs/plans/2026-10-10-ui-review-experiment-design.md) と [レビュープロンプト](ui-review-prompt-experimental.md) を併用する。対象の利用者、業務仕様、URL、代表データ、基準を固定してから確認する。現行UIの表示と操作を根拠にし、実装会話や作者の自己評価を合格根拠にしない。

## 1. 基準の種類

一般原則、顧客固有の採用事項、対象版の確定仕様、採用・却下・受容履歴を分ける。顧客ルールと確定仕様は対象プロジェクトの正本を参照し、このガイドへ複製しない。規格を参考にした確認と、経験則による改善提案も区別する。

「見づらい」「縦がよい」「余白を増やしたい」だけでは不具合としない。利用者・代表作業・再現条件・実害または採用仕様への違反を示す。採用済みの個別レイアウトを全顧客の一般ルールへ変えない。議事録の提案・未回答を確定仕様にしない。

## 2. 一般観点

規格番号は確認の参照先であり、採用されていない画面や機能の追加要求ではない。適用範囲や検証方法が不足すれば未検証と記す。

| ID | 観点と確認方法 | 参照・扱い |
|---|---|---|
| UI-G01 | 利用者が現在の作業・対象・次の操作を特定できるか。代表シナリオで見出し、項目、関連情報、主操作を確認する | 一般の情報設計観点。配置の好みは改善提案へ |
| UI-G02 | 金額、通貨、対象、選択、状態が区別できるか。色以外の手掛かりと文字の読みやすさを確認し、コントラスト違反は測定条件も示す | WCAG 1.4.1 / 1.4.3 / 1.4.11を参照 |
| UI-G03 | キーボードで代表操作を完了し、現在のフォーカスを追えるか。順序、閉じる操作、遮蔽、抜け出せない状態を実操作で確認する | WCAG 2.1.1 / 2.1.2 / 2.4.3 / 2.4.7 / 2.4.11を参照 |
| UI-G04 | 入力と操作部品に名前・役割・状態があるか。該当widgetの表示、DOM、キーボード挙動を照合する | WCAG 1.3.1 / 3.3.2 / 4.1.2、該当APG patternを参照 |
| UI-G05 | 待機、空、成功、失敗、対象外を取り違えないか。失敗時に対象と訂正方法を理解でき、結果を認識できるか | WCAG 3.3.1 / 3.3.3 / 4.1.3を参照。状態の表示内容は業務仕様に従う |
| UI-G06 | 重要な確定操作で対象・結果を確認できるか。誤入力の訂正、確認または取消の仕組みを、採用仕様と操作許可の範囲で確認する | WCAG 3.3.4を参照。確認ダイアログを一律に要求しない |
| UI-G07 | 指定幅・拡大条件で必要な情報や操作が欠けないか。重なり、切れ、スクロール、操作領域を確認する | WCAG 1.4.10 / 2.5.8を参照。二次元配置が必要な表等の例外を確認する |
| UI-G08 | 用語・単位・言語・同じ操作が採用仕様の範囲で一貫しているか。変更前後で対象と選択状態を誤認しないか | 一般観点と顧客仕様。切替や状態保持を未採用の機能要求にしない |

公式参考: [WCAG 2.2 Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/)、[WAI-ARIA APG Patterns](https://www.w3.org/WAI/ARIA/apg/patterns/)。

APGは対象widgetに応じて参照する。[Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) や [Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) などのパターンには、それぞれのキーボード操作・役割・状態の説明がある。表をすべてgrid扱いしたり、任意機能を必須扱いしたりしない。パターンとの差を直ちにWCAG違反と呼ばず、該当する達成基準と実害を確かめる。

## 3. 指摘を成立させる条件

不具合は、現在の対象版での観測と、期待を裏付ける基準が必要。一般観点から指摘する場合も、代表作業への具体的な影響を示す。最低限、次を記録する。

- 指摘ID、分類、根拠IDと採用状態、出典のパス/行またはURL/時刻。
- 観測結果、期待結果、初期状態、代表データID、再現操作。
- UTC日時、画面URL、source/runtime識別、画面幅・言語、画像/操作/DOM等の証跡。
- 利用者への影響、重大度、確信度、最小修正案。未決仕様を修正案で決めない。

観測と推論を分ける。画像だけの確認は操作未検証、sourceだけの確認は実画面未検証と記す。確認できた条件だけに判定を限定する。

## 4. 重大度・確信度・報告区分

| 重大度 | 影響 |
|---|---|
| P0 | 秘密・権限の重大な侵害、回復困難な業務データ損失や重大な誤処理に直結する |
| P1 | 主要業務を完了できない、誤った対象・金額・確定結果を利用者に認識させる等、重大な業務阻害が再現する |
| P2 | 一部操作や理解を妨げるが、妥当な回避策で対象業務を進められる |
| P3 | 影響が限定的な不整合・軽微な不具合。好みだけの提案は別区分とする |

確信度: 高=現行画面で再現し根拠が一致、中=観測はあるが一部条件や原因が未検証、低=仮説で再現・根拠が不足。低確信は確定不具合にせず確認事項とする。重大度と確信度は別々に付ける。

報告は「不具合」「確認事項・未決仕様」「好み・改善提案」に分ける。判定は入力で指定した停止重大度に従う。好みやP2/P3だけで停止条件を勝手に強くしない。適用基準や必要な検証が不足した項目は合格扱いしない。

受容済みの指摘は同じ適用条件では繰り返さない。再発、範囲外での再現、期限切れ、新しい影響・リスク増大があるときだけ、元の決定IDと再提示理由を付ける。修正済みという記録は現在の画面のPASSを意味しない。

## 5. 結果と基準更新

結果には確認範囲と未検証を必ず付ける。指摘0でも全画面・本番業務・WCAG適合全体の合格へ広げない。レビュー担当はUI、正本、ガイド、受容記録、チェック状態を編集せず、報告を返す。

新しい発言や改善案は、出典と決定状態を記録して利用者の判断へ返す。採用後に担当者が対象プロジェクトの正本を更新し、影響IDと旧確認の無効化を記録する。一般ガイドの変更は別の明示した変更として版を上げる。
